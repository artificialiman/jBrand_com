§1. Core Build

Element

<p>Content</p> = Element

Attributes (a property added to the atom, not a new atom)

<div class="card"> = Element + Attribute (class = "card")

An attribute doesn't change what an element is (a div is still a div), only how it's later treated by CSS/JS — same spirit as chemistry's isotopes: same core identity, different accompanying detail.

Void elements (no closing tag — a real exception, not a shortcut)

<img>, <br>, <hr>, <input>, <meta>, <link> = Void Elements
⚠ FALSE COGNATE <br> reads like an instruction (“break here”), but it's still just a tag — no HTML element ever executes anything. The verb-like names are English convenience, not a command being carried out. Python's imperative keywords will NOT share this property — this is the seam to watch for later.
> Memorization table No equation derives which elements are void: area, base, br, col, embed, hr, img, input, link, meta, param, source, track, wbr

Nesting (atoms containing atoms)

<div><p>text</p></div> = div is Parent, p is Child

Same-level Elements (share one Parent) = Siblings.

§2. Document Skeleton

Closes the loop on Core Build — the required scaffold every page needs. 

<!DOCTYPE html> = Document Type Declaration (not a tag — a signal to the browser, once, first line only)
<html> = Root Element (everything else nests inside this one)
<head> + <body> = the only two children <html> is supposed to have
⚠ FALSE COGNATE <head> and <body> sound anatomical/sequential — they are not “head happens first, body happens after” in any time-based sense. Both exist simultaneously the instant the page loads; the ordering is structural (metadata-container vs content-container), not temporal. This matters a lot once Python enters, where top-to-bottom order genuinely does mean “happens first.”

Metadata family

All live inside <head>, none of them render.

TagPurpose
<title>Text shown in browser tab / bookmark
<meta charset="UTF-8">Tells the browser which character set to expect
<meta name="viewport" ...>Tells mobile browsers how to scale the page
<link rel="stylesheet" href="...">⚠ EXTERNAL ONLY — pulls in CSS from outside
<script src="...">⚠ EXTERNAL ONLY — pulls in JS from outside
⚠ EXTERNAL ONLY <link> and <script src> are the two places HTML openly admits it cannot do something itself. They are not HTML's version of an acid — they are the hole in the beaker where an external acid gets poured in. See Section 5 for why this matters structurally.

§3. Text & Semantic Content

TagMeaning
<h1> through <h6>Heading (1 = most important, 6 = least)
<p>Paragraph (one block of prose)
<a href="...">Anchor (a link out of this document)
<strong>, <em>Semantic emphasis (meaning: “this matters” / “this is stressed”)
<b>, <i>Visual-only styling (bold/italic appearance, no meaning attached)

Real distinction, easy to conflate: <strong> and <b> can look identical rendered, but only one of them carries meaning a screen reader or search engine will register. Same trap as chemistry's Strength vs Concentration (§5 of the chemistry doc) — two things that look the same from a distance are answering different questions. 

<ul> + <li> = Unordered List (bullet, no inherent sequence)
<ol> + <li> = Ordered List (numbered, sequence is part of the meaning)
⚠ FALSE COGNATE “Ordered” here means displayed with a fixed sequence marker, not “executed in order.” HTML has no execution at all — this is purely visual/semantic sequence, not the order-of-operations sense the word will carry once Python arrives. 
<table> + <tr> + <td> = Table (rows, then cells inside rows)
<th> = header cell (semantically a label, not just a styled cell)

§5. HTML's Bonding Equivalent — and where it structurally runs out

This is the section where the chemistry parallel has to be stated honestly rather than forced.

Structural Bond Element + Element (nested) = Structural Bond (parent holds child — always present, HTML alone provides this)
⚠ EXTERNAL ONLY Element + CSS Rule = Styled Bond
⚠ EXTERNAL ONLY Element + JS Event = Behavioral Bond

Chemistry has three bonding types (covalent, ionic, metallic) that are all internal to the atoms doing the bonding — the electrons involved belong to the atoms themselves. HTML only ever has one bond type that is truly its own: structural nesting. Every other kind of “bonding” a page needs (appearance, behavior) is borrowed wholesale from a different language entirely. This is not a gap in this book's research — it is a true structural fact about HTML.

HTML alone Structure only, no appearance rules, no behavior, no state.

This is the single most important line in this section. A raw HTML file with no CSS and no JS is not “basic” or “unfinished” — it is complete, on its own terms. HTML was never missing something; it was never designed to have appearance or behavior in the first place. Compare: chemistry's non-polar covalent bond is not a “weaker” ionic bond — it's a different, complete thing.

§6. Acid / Base / Salt Equivalent — Deployment Role, not Reaction

Per the working framework: this axis is not about a chemical property, it's about what role a piece of code plays in its environment. HTML's honest position on this axis:

HTML Document = Base, always A pure receiver — accepts whatever is poured into it. HTML alone = never an Acid (it has no mechanism to drive change into anything else).

HTML cannot act on another file, cannot mutate state, cannot trigger anything on its own. It only ever receives — content poured in by a human author, styling poured in by CSS, behavior poured in by JS. On the acid/base axis this book is building, HTML sits permanently on the Base side. There is no “strong HTML” vs “weak HTML” the way there's strong/weak acid — reactivity strength doesn't apply to something that never initiates a reaction in the first place.

Static HTML file, no build step = Salt equivalent Stable, sitting there, done. Templated HTML (rendered from data at build time) = still Salt — the “reaction” already happened upstream.

A plain .html file on disk is already the settled, stable “product” — same rung as your report-card pages once generated. HTML never occupies the ester/precipitate/emulsion distinctions on the vertical axis either — a saved .html file is about as close to pure “dissolved into the filesystem, inert, done” as an artifact gets.

§7. Redox Equivalent — Deferred, Correctly

HTML = no Reducing Agent, no Oxidizing Agent Redox is about electron transfer and agents named for their effect on something else. HTML has no mechanism to transfer anything to anything — it does not act on other files, other elements, or itself. There is no honest redox-equivalent content to put here for HTML alone.

This section stays empty on purpose. It's the clearest, starkest statement in this whole book of the thing you raised at the very start: chemistry vocabulary describes phenomena, code vocabulary issues commands — and HTML, alone, issues none. This gap is where the Python book's redox section will have its real content; flagging the gap here is more honest than padding it with a forced analogy.

✦ ✦ ✦

§8. Thermodynamics Equivalent — Same Verdict, Same Honesty

HTML = no Spontaneity, no Combustion-equivalent, no Electrolysis-equivalent All three of the energy-economics categories (free/self-sustaining/forced) describe execution — something happening over time, paid for somehow. HTML has no execution.

A browser parsing HTML is the browser's activity, not HTML's — the same way a rock doesn't “do” anything just because gravity is acting on it. This section, like Section 7, stays deliberately blank. Two blank sections in a row is the honest shape of “declarative structure has no engine,” not a failure to find a mapping.

§9. Forms — the closest HTML gets to inviting a reaction

If there is one place HTML gestures toward acid-like behavior without ever crossing into it, it's forms — worth its own short section because it's the seam where user input threatens to look like state.

⚠ EXTERNAL ONLY <form action="..." method="..."> = a declared intention to send data somewhere

<input>, <textarea>, <select> = fields (hold a value, but do not act on it).
<button type="submit"> = a labeled invitation to trigger a submission.

> Crucial honesty check The <form> tag does not send anything. It does not run. It declares, in structure alone, “if a submission happens, send it here, this way” — the actual sending is carried out by the browser as a program, external to HTML entirely. Even the most action-shaped tag in the whole language stays inert on its own. This is the strongest single piece of evidence in this book for the claim that chemistry vocabulary codifies phenomena, code vocabulary commands machinery — and HTML sits right at the edge of that boundary without ever actually stepping over it.

§10. Distinguishing Pairs

PairMeaning
<div> vs <span> Both meaningless containers; div = block-level (starts new line), span = inline (sits within text)
id vs class id = exactly one match per page, unique identity; class = many elements, shared identity
href vs src href = “go there instead” (a reference/link out); src = “bring that here and show it” (an embed)
Block-level vs Inline Does it force a new line (block), or sit inside existing text flow (inline)
⚠ FALSE COGNATE id sounds like a permanent, chemistry-style identity (like proton count), but it is purely a lookup convenience — nothing enforces uniqueness except convention and tooling. HTML will render a page with duplicate ids; it just breaks the assumption that CSS/JS rely on. Not a hard law the way proton count is.
> Easy to conflate href and src both take a URL. href never brings content into this document; src always does. One is a pointer, the other is an import.

§11. Attributes & Values — HTML's “Mole & Stoichiometry” Equivalent

Chemistry's mole section is the bridge currency — the thing that makes every other section countable and combinable. HTML's closest equivalent isn't a unit of measure; it's the attribute=value pairing itself, because it's the one mechanism every single tag above relies on to carry any configuration at all. 

Attribute Name + "=" + "Value" (in quotes) = Attribute-Value Pair
class="card", href="page.html", alt="a description" = all the same underlying pattern
⚠ FALSE COGNATE — the most important one in this book = here means “this attribute HAS this value” — a static label, decided once, sitting there. It is not assignment in any executable sense; nothing is being computed or stored in memory. The identical glyph in Python will mean “take whatever's on the right, store it under the name on the left, right now, at this specific point in execution.” Same symbol, two completely unrelated jobs — the single clearest place this whole book exists to catch you.
> Multiple attributes on one element Space-separated, order does not matter. 
<img src="x.jpg" alt="a cat" width="200"> = same as any reordering of those three

Real contrast to flag now, cash in later: attribute order on one tag is irrelevant (declarative, all-at-once). Argument order in a Python function call is not irrelevant unless named explicitly. This is where “HTML as control group” pays off hardest — you already know attribute order doesn't matter, so when Python parameter order suddenly does, that will register as a felt violation, not just a rule to memorize.

§12. Summary for a New Reader

HTML is the one member of this planned book-pair that behaves almost exactly like a chemistry equation system: pure structure, no hidden state, order mostly irrelevant, nothing executes. Every section above that chemistry would normally fill with rich content — redox, thermodynamics — stays honestly blank here, because HTML has no mechanism for the thing those sections describe: driven change over time.

Where HTML brushes up against acting (forms, <script src>, <link>), it never actually crosses into acting itself — it only ever declares an intention or opens a door for something external to act through.

The one section carrying outsized weight for what comes next is Section 11: the = sign, identical in appearance to Python's assignment operator, doing a completely different job. That single collision is the seed of the whole reason this book exists — to use a language you already know cold as the control group that catches Python's cracks the moment they appear.
