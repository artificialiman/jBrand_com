§1. Core Build

⚠ FALSE COGNATE (HTML §1) HTML tags look like commands (<br> reads like “break here”) but never execute. Python keywords (if, for, def, return) are the real thing — HTML's tag‑verbs only impersonated. These genuinely cause something to happen, in a specific place in the running program, at a specific time.

Statement

# Keyword + Expression + Colon + Indented Block = Statement
if condition:
    do_something()

Assignment — the line HTML's Section 11 warned about

# Name + "=" + Value = Assignment
x = 5
⚠ FALSE COGNATE (HTML §11) — CASHED IN HTML's = meant “this attribute permanently has this value,” decided once, no computation, no memory. Python's = means: evaluate the right side right now, store the result under the name on the left, at this exact point in execution. Same glyph, unrelated job. This is the single collision the whole two‑book project was built to make you feel, not just know.
⚠ ORDER/STATE 
x = 5
x = x + 1   # x is 6
x = x + 1
x = 5       # x is 5

Identical two lines, reversed order, different final state. No chemistry equation and no HTML line has ever behaved this way — order was always either irrelevant (HTML attributes) or descriptive‑only (chemistry, “read the equation any direction”). This is the first genuinely new mechanic in this whole three‑book project.

Data types — the periodic table, the closed memorizable set

TypeDescriptionExamples
intWhole number3, -12, 0
floatDecimal number3.14, -0.5
strText, quoted"hello", 'world'
boolTrue / FalseTrue, False
NoneTypeNothing / absenceNone

▸ Memorization table — nothing derives which literal syntax maps to which type; you just have to know quotes mean str, a decimal point means float.

⚠ FALSE COGNATE (HTML §3) Python's None and HTML's empty/void elements (<br>, <hr>) can both feel like “nothing here” — but None is an actual value that exists and can be checked, passed around, and compared. A void element isn't “empty content,” it's a tag that structurally never had a content slot to begin with. Absence‑as‑value vs absence‑of‑slot are different ideas wearing similar clothes.

§2. Program Skeleton

⚠ ORDER/STATE A module is a single .py file, top to bottom — always.
⚠ FALSE COGNATE (HTML §2) — CASHED IN HARD HTML's <head> and <body> “sound sequential but aren't” — both exist the instant the page loads, simultaneously. A Python file's top‑to‑bottom order is the opposite of that: it is genuinely sequential. Line 3 can use something line 1 created; line 1 cannot use anything line 3 creates. This is the exact temporal claim HTML's doc told you not to assume — and here it's finally true.

Import

import module_name   # pulls in code defined elsewhere

▸ Real contrast worth naming: HTML's <link> / <script src> were “the hole in the beaker” — HTML could never do that job itself, only invite something else to. Python's import also reaches outside the current file, but Python could, in principle, define that same code right here instead — importing is a convenience/organization choice, not a structural admission of powerlessness.

if __name__ == "__main__"

if __name__ == "__main__":
    # only run if this file was launched directly, not imported
⚠ ORDER/STATE — real exception This line only makes sense once you know Python sets a hidden variable, __name__, differently depending on how the file was started. Nothing about the syntax announces this; it's a convention resting on a mechanism you have to be told about once.

§3. Text & Sequence Content

Strings, Lists, Tuples

str   = ordered sequence of characters, indexable: "hi"[0] = "h"
list  = ordered, mutable sequence: [1, 2, 3]
tuple = ordered, immutable sequence: (1, 2, 3)
⚠ FALSE COGNATE (HTML §3) HTML's <ol> (“ordered list”) meant visual/semantic sequence only — a numbered marker, nothing about execution. Python's list ordering is real and load‑bearing: list[0] and list[1] are genuinely different memory positions you can act on individually, not just numbered for display. The word “ordered” is finally doing the job its English meaning always implied.

Dict

# key/value pairs, insertion order preserved since 3.7
{"name": "Amara", "age": 20}
⚠ FALSE COGNATE (HTML §11) A dict entry looks like an attribute pair (key: value vs key="value") but behaves like Section 11's = collision, not like an HTML attribute — the dict is a live, mutable object sitting in memory; reassigning a key changes state, the same file, at the moment that line runs. An HTML attribute never “changes” mid‑document; a dict routinely does, line by line.

Set

# unordered, no duplicates
{1, 2, 3}

▸ Real exception to the ordering pattern just established — sets exist precisely to throw ordering away. Don't over‑generalize “Python collections all care about order” from list/dict; set is the honest counter‑case, kept for a specific reason (fast membership checks, no duplicate tolerance).

f‑strings

f"text {variable} more text"   # variable must already exist above this line
⚠ ORDER/STATE The variable inside the {} must have been assigned before this line runs.

§4. Functions & Reusable Blocks

▸ HTML's Section 4 was about pulling outside media in as a static, inert embed. Python's actual equivalent isn't importing files (that was Section 2) — it's the function itself: a block you define once, and embed a call to anywhere you want its effect to happen again.

Definition

def function_name(parameter):
    # indented block
    return value
⚠ ORDER/STATE — the most important fact A function's body doesn't run when it's defined — only when it's called. 
def greet():
    print("hi")      # nothing happens yet

greet()              # THIS is when "hi" prints

This has no HTML equivalent at all: HTML has nothing that is “written but dormant until separately triggered.” A <p> tag renders the instant it's parsed. A Python function can sit fully written, doing nothing, for the entire remaining life of the program, until something calls it — possibly never.

Parameter Order

def describe(name, age):
    ...

describe("Amara", 20)           # positional — name="Amara", age=20
describe(age=20, name="Amara")  # keyword — identical result, order‑independent
⚠ FALSE COGNATE (HTML §11) — CASHED IN HTML told you attribute order never matters, full stop, always. Python's parameter order matters conditionally — positional calls are order‑strict, keyword calls aren't. This is exactly the “felt violation” the HTML book predicted: you already know order‑doesn't‑matter as a gut feeling from attributes; Python punishes that gut feeling the moment you drop a keyword.

§5. Python's Bonding Equivalent — Coupling

HTML's only true bond was structural nesting; everything else was external and borrowed. Python's bonding equivalent is about how tightly one piece of code depends on another's internal state.

CategoryDescriptionAnalogy
Pure Function Uses only its own parameters; no outside variables touched ~ Non‑polar Covalent
Coupled Function Reads a variable defined outside itself ~ Polar Covalent
Side‑Effect Function Modifies a variable defined outside itself ~ heading toward Ionic
Global mutable state Touched from many places ~ Ionic Lattice
⚠ ORDER/STATE A Coupled or Side‑Effect function's behavior can change depending on what ran before it — a Pure Function's behavior cannot, ever, regardless of what ran before it.

This is the real, checkable test for “how coupled is this”: if you can run a function twice with the same arguments and ever get two different answers, something outside its parameters is involved, and it now lives somewhere on the coupling scale above pure.

§6. Acid / Base / Salt Equivalent — Deployment Role

Where HTML had one honest, permanent answer (always Base, never Acid), Python is where this axis actually gets to do its full job, because Python is where real acids exist.

RoleDescriptionExample
Acid Script that runs, acts on other files/systems, then exits Build pipeline, data‑migration script, CSV→HTML generator
Base File/object that only holds data and waits to be acted on Config file, template, data class with no mutating methods
Salt Generated output, stable and done Rendered student page, compiled artifact
Water Side‑effects / logs / console output Printed status messages, debug output
Acid + Base = Salt + Water 
CSV + report_template.html (+ generator script)
    = rendered student page (Salt) + console output (Water)

This is close to a literal description of the report‑generation pipeline itself: the CSV broadsheet and the HTML template are both inert Bases sitting still; the Python generator script is the Acid that drives a reaction between them; the individual student HTML pages that drop out afterward are the Salt — stable, done, sitting on disk, no longer needing the script that made them to keep existing.

Strong vs Weak Acid

# Strong Acid: runs deterministically to full completion, no conditional early exits
# Weak Acid: partial — has branches, early returns, conditions where it doesn't fully "ionize"
⚠ ORDER/STATE Whether a script counts as Strong or Weak on this axis can only be known by tracing its actual execution path for given input — the same lines of code can behave Strong for one input and Weak for another.

A generator script might run “strong” (fully, deterministically) on 21 complete student rows and “weak” (early‑exit/flagged) on the 2 incomplete ones (Dorcas, Habitat) in the exact same run. Same acid, different strength, depending what it's reacting with.

Buffer Solution

A function/module with its own error handling and sane defaults, self‑stabilizing against bad input, vs a fragile one‑off script that breaks the moment conditions shift even slightly.

Vertical axis — does the output stay dissolved, or separate out?

StateDescriptionAnalogy
SaltIn‑memory variable, gone when the process endsFully dissolved
EmulsionCache / session‑scoped state, held together only while something maintains itEmulsion
PrecipitateWritten file, persists after the process ends, same machinePrecipitate
EsterPortable/exported artifact (built package, Docker image, compiled binary)Fully separated
⚠ ORDER/STATE runs through this entire axis When you check “where is this output right now” changes the answer. A dict built mid‑function is Salt while the function is running, and simply ceases to exist the moment the function returns — chemistry's dissolved salt doesn't vanish when you stop looking at the beaker; a Python variable's “solution” can disappear from under you the instant its enclosing function ends. This is called scope, and it has no equivalent honesty‑requirement in either prior book.

§7. Redox Equivalent — Fully Populated, Flexibly

This was the section HTML left explicitly empty. Per the working framework, this one isn't pinned to a single rigid mapping — it flexes per concept, same as chemistry's redox agents being named for their effect on something else, not on themselves.

Reducing Agent Function/operation that causes another variable/object to change, while itself changing in the act. The other variable is “reduced” — something was added/changed onto it.
Oxidized Party The thing that gets consumed/altered by something else acting on it.
⚠ Same backwards‑naming trap An agent is named for what it does to the other thing, not for its own visible behavior. A function called apply_discount(cart) is the reducing agent — it causes cart to change; cart is the oxidized party, the thing that got acted upon.
⚠ ORDER/STATE — load‑bearing here more than anywhere else 
mutating_function(shared_list)   # THEN read shared_list  => sees the mutation
read shared_list                 # THEN mutating_function(shared_list)  => doesn't

This is Python's honest equivalent of anode/cathode polarity depending on cell type: whether a given piece of state has “already been reduced” depends entirely on where you're standing in the execution order, not on anything you can read off the variable's definition alone.

Dependency chain / call order

# A calls B calls C  => data/effects flow A -> B -> C, NOT C -> B -> A

Chains of function calls are Python's most literal redox structure: at each link, one function is the agent causing change in what it calls or touches, and that changed thing becomes the input further down the chain. Trace the chain in the wrong direction and the whole “who reduced whom” story falls apart — same as misreading which electrode is the anode in a galvanic vs electrolytic cell.

§8. Thermodynamics Equivalent — Execution Economics

HTML had nothing here because it has no execution. Python has real execution, so per the framework this maps to who pays, how much, and for how long a piece of code keeps running — separate from kinetics (how fast), which stays its own lane below.

Economic CategoryDescriptionPython Pattern
Spontaneous Free, runs once given permission, no ongoing cost Pure computation / one‑shot script
Combustion Continuous input required, but self‑sustaining momentum once started Running server / event loop
Electrolysis Massive forced input, zero self‑sufficiency, stops dead the instant force is withdrawn Timer/cron‑driven callback (scheduled job)
⚠ ORDER/STATE Which economic category a piece of code falls into can change based on where it's called from — a function that's “spontaneous” called once in a script becomes part of a “combustion” system the moment it's wrapped inside a running server's request handler.

Kinetics — kept deliberately separate

# Time/space complexity (Big‑O) = HOW FAST, not who's paying or how long it runs
# O(1), O(log n), O(n), O(n log n), O(n²) ...

A script can be Spontaneous (§8, free, runs once) and still be O(n²) (slow, this section) — being “free to trigger” and “fast once triggered” are different questions, same as chemistry's ΔG (does it happen) vs K (where does it end up) vs rate (how fast) all being related but genuinely separate questions.

Catalyst‑equivalent

# Caching / memoization: gets you to the answer faster, does NOT change WHAT the answer is

Same warning chemistry gave about catalysts and equilibrium: caching a function's result changes speed on repeat calls, never changes correctness of the result itself. A cache with a bug that changes the actual returned value isn't “a fast catalyst,” it's a broken function — the same category error as thinking a catalyst could shift where a reaction settles.

§9. Forms Equivalent — where Python actually crosses the line

HTML's form section was the closest that language got to acting, and the whole point of that section was that it never actually crossed into acting — the browser did the real work, externally.

input()

name = input("What's your name? ")   # execution PAUSES here until a human responds
⚠ ORDER/STATE This is the real crossing HTML's <form> gestured at but never made. <form> declared an intention; the browser (external) carried it out. input() doesn't declare anything — it is the act itself, and it actually halts the program's forward progress, mid‑execution, waiting. There is no HTML equivalent to a line of code pausing; a parsed HTML document has no concept of paused‑and‑waiting at all.

open() / write

open("file.txt", "w").write("data")   # Python actually writing to disk, right now

Compare directly to HTML's <form action="...">: HTML only ever declared where data should go, never sent it. open(...).write(...) is Python actually doing the sending — no external browser required, no admitted powerlessness. This is Python holding the acid HTML could only gesture at pouring.

§10. Distinguishing Pairs

PairMeaning
= vs == Assignment (store a value) vs Comparison (ask “are these equal”, returns True/False)
list vs tuple Mutable, changeable after creation vs Immutable, fixed forever once made
is vs == Same object in memory vs Same value
return vs print Hands a value back to the caller vs Displays text, gives nothing back
Argument vs Parameter Parameter is the name in the def; argument is the actual value passed at call time
⚠ FALSE COGNATE (HTML §11) — the single most common bug if x = 5: is not “checking if x is 5,” it's an attempt to assign inside a condition, and Python actually forbids this exact mistake with a syntax error — one of the few places the language protects you from the very collision this whole book was built around.
Real trap Two different lists holding identical numbers are == True but is False — same value, different object. No HTML pair works this way; HTML has no concept of object identity separate from content at all.
Beginner conflation A function that prints its answer but doesn't return it looks like it “worked” (you saw the output) but any code trying to use that function's result gets None — the value was shown, never handed back.

§11. Variables & Scope — Python's Mole & Stoichiometry

HTML's bridge currency was the attribute=value pair — the mechanism every tag relied on. Python's bridge currency is scope: the rule governing which name refers to which value, at which point in execution — the concept every other section above has quietly leaned on.

⚠ ORDER/STATE Local scope: variable defined inside a function — exists only during that call, gone after return.
Global scope: variable defined outside any function — exists for the whole module's lifetime.

Shadowing

x = 5                 # global

def f():
    x = 10            # this x is DIFFERENT — local, doesn't touch the global
    return x

f()      # => 10
print(x) # => still 5
⚠ ORDER/STATE — the single most disorienting fact The same name, x, can refer to two completely different values depending purely on where in the file's structure a line sits — not because anything overwrote anything, but because scope partitions the name itself. HTML has nothing like this: an id either exists on the page or doesn't; it doesn't quietly mean something different depending which <div> you're standing inside.

Function Signature — the “stoichiometry” of a program

def convert(celsius):
    return celsius * 9/5 + 32
# 1 argument in -> 1 value out, exactly, every call, same ratio

Just as chemistry's mole section revealed that every “A + B = C” from earlier sections secretly encoded a ratio, this reveals that every function signature used throughout this book secretly encoded an input‑to‑output contract the whole time — parameters and return values are the real “stoichiometry” of a Python program.

⚠ FALSE COGNATE (HTML §11) — cashed in a second time A function call, describe("Amara", 20), looks like it's just “filling in slots” the way attributes filled in a tag's configuration. But each call is a fresh, ⚠ ORDER/STATE event — a new local scope is created, used, and destroyed, every single time the function runs. An HTML tag's attributes don't get “recreated” on some kind of repeated firing; they just sit, once, forever, in the file.

§12. Summary for a New Reader

Python is the half of this book‑pair where the sections HTML left honestly blank — redox, thermodynamics — finally get their real content, because Python is where code stops describing structure and starts issuing commands against a state that changes as those commands run.

The single flag that had almost no work to do in the HTML book, ⚠ ORDER/STATE, is the dominant fact of nearly every section here: the same characters, evaluated in a different sequence, produce a different program.

The collision seeded hardest across both books — HTML's = meaning “this attribute permanently has this value” versus Python's = meaning “compute the right side now, store it under this name, at this exact moment” — is the one piece of evidence that best honors the distinction raised at the very start of this project: chemistry's vocabulary was built to describe phenomena that would happen with or without the words for them; HTML's vocabulary describes a structure that sits still the instant it's written; Python's vocabulary is the first of the three that actually does something the moment you run it, in the order you wrote it, whether you meant it to or not.
